🪨 SOLID

September 30, 2026 · 3 min read
Eldar Paşazadə
Software Engineer

SOLID is a set of guidelines for making object-oriented software easier to change, test, and maintain.

In the year 2000, an acclaimed software engineer Robert C. Martin aka Uncle Bob published a paper titled “Design Principles and Design Patterns” in which he introduced the SOLID principles. They fundamentally changed the way developers approach object-oriented design, emphasizing the importance of modularity, maintainability, and extensibility.

Single Responsibility Principle​

A function or module should have one reason to change. Keep unrelated jobs in separate places.

For example, calculate a total separately from displaying it:

const calculateTotal = prices =>
  prices.reduce((sum, price) => sum + price, 0);

const printTotal = total =>
  console.log(`Total: ${total}`);

If the display format changes, the calculation function stays the same.

Open/Closed Principle​

Software entities should be open for extension, but closed for modification. Add a new behavior by introducing a new implementation rather than repeatedly editing stable code.

Checkout receives a discount object with an apply method:

class NoDiscount {
  apply(total) {
    return total;
  }
}

class TenPercentDiscount {
  apply(total) {
    return total * 0.9;
  }
}

const checkout = (total, discount) => discount.apply(total);

checkout(100, new TenPercentDiscount());

To add another discount, create a class with an apply method; checkout stays unchanged.

Liskov Substitution Principle​

A subtype should be usable wherever its base type is expected without breaking the program's behavior. A subtype should honor the promises made by its parent type.

This principle is named after Barbara Liskov, a pioneering computer scientist who introduced the idea of behavioral subtyping, which explains when one type can safely replace another.

If every Bird is assumed to fly, a penguin cannot meet that contract. Keep flying as a separate capability instead:

class Bird {
  eat() {}
}

class Raven extends Bird {
  fly() {
    console.log("Flying!");
  }
}

class Penguin extends Bird {}

const letFly = bird => bird.fly();

letFly(new Raven());

Now a penguin can be a Bird without pretending that it can fly.

Interface Segregation Principle​

Clients should not have to depend on methods they do not use. A robot can work without needing an eat method:

class Human {
  work() {}
  eat() {}
}

class Robot {
  work() {}
}

const startWork = worker => worker.work();
const serveMeal = eater => eater.eat();

startWork(new Robot());
serveMeal(new Human());

The work client uses only work, while the eat client uses only eat; Robot does not need an irrelevant method.

Dependency Inversion Principle​

High-level business logic should depend on an abstraction, not on a specific tool. An order receives a sender that follows the send contract:

class EmailSender {
  send(message) {
    console.log(message);
  }
}

class Order {
  constructor(sender) {
    this.sender = sender;
  }

  place() {
    this.sender.send("Order placed!");
  }
}

new Order(new EmailSender()).place();

Order receives its sender instead of creating one itself, so another sender can be substituted without changing the order logic.

Redundant?​

SOLID is a bit reductive. Five letters can make a broad set of design trade-offs look like a complete checklist. Three ideas are often enough:

  1. Keep responsibilities cohesive.
  2. Make dependencies and contracts explicit.
  3. Add flexibility only where change is likely.

The other principles are useful ways to apply those ideas, not rules every design needs to satisfy independently.
